# 5.5 - Make it pretty (an Elixir refactoring story)

It's been a couple of weeks now that I've been working on a chess app written in Elixir. To be more specific, I am working on a blog post series that's meant to walk you through a long-term project of building a chess application from zero to production. The main goal of the series is for you to write the project on your own, and I mostly give you some structure and some tests to help shorten that feedback loop. I do share my code as well, but you're encouraged to write things on your own.

Over the last couple of blog posts I've been teasing at a refactoring coming soon - there were a couple of places in the code where adding new behaviour felt a bit awkward. 
- Shifting context was always a pain 
- Bugs were creeping up in weird places due to tight coupling
- `Game` module is over 75% of the codebase

So today I am doing a bit of a different post, one where instead of focusing on new functionality, on adding new use cases - we'll instead focus on cleaning up our mess. We usually start with the tests, today they will only make an appearance at the end. Or if I wanted to spoil things a bit, it's the very absence of changes that will be the topic of conversation.

## Context
I want this post to be pretty self-contained, so I thought I'd start with a quick recap of what we have so far.

### Board representation
We decided to go with a map representation for the board `%{square() => piece()}`. It's not the optimal decision for the BEAM, and Erlang's [binbo](https://github.com/DOBRO/binbo) has instead gone for bitboards - we might do the same at a later stage, for now our `Board` module is pretty self-contained so we should be able to switch from one to the other fairly easily.

### Application entry point
We have a single module for our application entry point with 3 functions. I've added a comment above each to quickly recap the functionality.
```elixir
defmodule ExChess.Game do
    # creates a new instance of the `Game` struct with a board in the default chess rules starting position
    @spec new() :: t()
    def new()

    # plays the next move for the current chess game, returns the new game state when the move is successful
    # otherwise returns a generic invalid move error
    @spec move(t(), Move.t()) :: t() | error()
    def move(
        game = %__MODULE__{board: board, special_rules: special_rules},
        move = %Move{}
      )

    # returns a list of square coordinates that a piece can legally move to
    @spec list_legal_moves(t(), Square.t()) :: [Square.t()]
    def list_legal_moves(
        %__MODULE__{board: board, special_rules: special_rules},
        from_square = %Square{}
      )
end
```

### Progress
Let's first start with what we haven't done yet - we don't track the game history, we don't track time taken per turn, we only have "local multiplayer". 

One of the simpler rules we haven't added yet is turn checking - you can still move two white pieces in a row, but that does not affect our work today in any way.

Another rule we don't yet have is game end detection - checkmates, stalemates, resignation, etc...

Other than that, all pieces can move as expected, checks are respected, we have en passant, castles, pawn promotions - all of that good fun.

### Structure
Our code is currently almost entirely in the `Game` module in private functions - the only other modules we have are some small data structures and a couple of helper functions: `Piece`, `Square`, `Move`, `Board` and `SpecialRules` - but all of those are extremely slim.

Here's how the dependency graph looks:
```text

```

And all files are in the project's root:

To give you an idea of the size of those - the five helper modules are 30 lines of code on average, and the `Game` module is about 450 lines. As you might have assumed, we will be breaking that up a bit today.

## I - Don't Over-Repeat Yourself
This first bit is all about striking a balance. Everyone's heard of DRY but have you heard of DORY? And no, I am not referencing the blue fish with corrupt memory.

Of course you haven't heard of DORY. I just made it up.

If I have to be perfectly honest, I did find an old blog post using the same abbreviation but it was used to mean 'DO repeat yourself' and talked specifically about distributed systems, hence I am happy to claim "Don't Over-Repeat Yourself" as my own creation.

Back to the point.

There is one fundamental problem present in the vast majority of software development - the unknown unknowns. When you do not know what to expect, it's easy to prepare for the wrong version of the future. We don't get to Doctor Strange our way through with the time stone.

However, us software engineers, arrogant as we are, do not merely accept restrictions such as time and space, every one of us insists they are an oracle, but none of our teammates are. And so we do what we do worst - abstractions. 

*DRY! Reuse! I shan't repeat a single line twice!* said the peasant.

It's me. I am the peasant. And that my friends, is what brought me here. 

As a **former** DRY addict, let me lead the way through this tunnel I know all too well. And yes. I will relapse in the next tunnel. Stop judging me.

### The problem
I *really*, *reaaallyy* thought, that I could consolidate all my move validation logic in a single `valid_move?` function.
I was right. 

*The end*

Here's a very quick summary.

**Was it possible?** </br>
*Absolutely.* 

**Did it work?**  </br>
*You bet it did.* 

**Was it worth it?**  </br>
*Not one bit.* 

**Did it hurt?** </br>
*Like the depths of hell.*

**What did it take?** </br>
***Four** f\*cking flags... I am passing in **four** f\*cking boolean flags.*

Now, admittedly, one of the four flags was just me doing some premature optimization in a code base which is very much not optimized. But hey where's the fun without some of that?

The point is, there are three different places in the code that needed some form of move validation:

- `Game.move` - the full list of requirements
- `Game.list_legal_moves` - skip validating: promotion,  movement patterns
- `Game.square_attacked?` - skip validating: promotion, check, special moves

We are therefore splitting up `valid_move?` into five functions:
- `valid_promotion?`
- `basic_valid_move?`
  - `from_square` is not empty
  - `to_square` is within board bounds
  - Not taking own piece
- `normal_piece_move_verify`
- `advanced_piece_move_verify`
- `square_attacked?`

There were quite a few functional changes especially to the two `X_piece_move_verify` functions which now are also tasked with evaluating the move type on legal moves.

How does the calling code look? Obviously bulkier. We'll look at it later in the blog post though - after discussing the rest of our changes.

Before we move on, I do want to give some credit to DRY too. I added a new `Square.compare` function that returns a tuple with 2 integers - `{file_shift, rank_shift}` since I was doing that in 4-5 places.

## II - No gods 'round 'ere

So I mentioned this earlier, but from a code base of around 600 lines of code (ignoring tests) - 450 (75%) are in the `Game` module.

450 lines of code isn't all that bad at all, but 75% of the total code base in a single file is obviously not great either.

Similar to DRY though, my opinion to the god object/class(/module?) antipattern is somewhat controversial. 

I prefer ***by far*** having a huge `Game` module over the same big ball of mud distributed into 200 3-line functions that I then have to untangle in order to get a general idea of what is happening in the code base. I'll take underengineered over overengineered any day of the week. 

The same is even more true when it comes to architecture. I'd rather have to pull microservices out of a monolith then consolidate a bunch of nanoservices. I'd rather extract a slow operation into an event-driven long running workflow, then have a kubernetes cluster hosting a distributed redis cache and multiple instances of my api for a system with less than a million records and 10 tables handling about 100 requests per second at peak traffic.

Having said that, I do like breaking things up a bit once the patterns have emerged. I just think it's something you postpone until the moment you start feeling some discomfort while working on the code, rather than operating with the impression that we can foresee the future requirements and try to split up our code fittingly in preparation.

Okay, so I shared the project structure and the modules' dependencies earlier in the blog post. Let me share with you the results of the refactor.
```text
├── lib
│   ├── board.ex
│   ├── game
│   │   ├── move_context.ex
│   │   ├── move_type.ex
│   │   ├── piece_targets.ex
│   │   ├── state
│   │   │   ├── board_manager.ex
│   │   │   └── special_rules_manager.ex
│   │   └── validators
│   │       ├── basic.ex
│   │       ├── normal_moves.ex
│   │       ├── promotion.ex
│   │       ├── special_moves.ex
│   │       └── square_under_attack.ex
│   ├── game.ex
│   ├── move.ex
│   ├── piece.ex
│   ├── special_rules.ex
│   └── square.ex
```

As you may have noticed, at the root of the repository nothing has changed. We have all of the modules the developer using our library will operate with.

The only change from those root modules is `Game`.  The former big ball of mud is now less than 70 lines of code. It only has a couple of public functions, the struct definition, and one 15-line private function for the functionality used by both `move` and `list_legal_moves`.

Where did the other 400 lines go? Into all those files in `lib/game/`.

Let's go through the list.
`Game.MoveContext` - A data structure used internally to represent the full context of a move including the game state, the inputs, and some calculated fields such as the pieces affected by the move.
`Game.MoveType` - Type specs to represent the union of possible atoms representing the move type.
`Game.PieceTargets` - This is used by `list_legal_moves` as a starting point of possible targets, before those later get evaluated based on the game state.

`Game.State.BoardManager` - `update` function used to apply a move on the board
`Game.State.SpecialRulesManager` - `update` function used to update the special rules state after a move is made

`Game.Validators.Basic` - validates that a move respects the board bounds, that a piece is found, that an ally piece is not targeted.
`Game.Validators.NormalMoves` - validates the move is allowed for the selected piece based on board state, and returns the move type
`Game.Validators.SpecialMoves` - same as `NormalMoves` but specifically for castles and en passant.
`Game.Validators.Promotion` - validates a promotion type is selected when (and only when) a pawn moves to the last rank
`Game.Validators.SquareUnderAttack` - validates whether a square is under attack by an opponent piece

And here's how the module dependencies look (ignoring the types in the root directory).
```text
MoveContext
MoveType
PieceTargets

State.BoardManager → MoveType 
State.SpecialRulesManager → MoveType 

Validators.Promotion
Validators.Basic → MoveContext
Validators.NormalMoves → MoveContext, MoveType
Validators.SquareUnderAttack → Validators.Basic, Validators.NormalMoves
Validators.SpecialMoves → MoveContext, MoveType, Validators.SquareUnderAttack
```

And of course, the game module uses all of the above.

I see three major advantages to this new project structure:
- Just based on the module dependencies you can learn for example that the special moves validation needs to check if certain squares are under attack or not.
- A quick scan of the files and directories already gives some idea of what business logic we have.
- For most devs and their tooling, jumping between files is substantially easier than between different lines in a file.

And with that our codebase went from a big ball of mud to a distributed big ball of mud. Great success.

Jokes aside, I am really happy with the results - moving around the codevase feels so much quicker and more intuitive than it did beforehand.

## III - Idolize idioms

So far we've been focusing on very specific and language-agnostic types of code smells. When it comes to idioms, those differ greatly from one tool to another, hence they are also inherently subjective. 

Then why is it something we want to strive for? It sounds like it's more tradition than it is a practical choice. 

I can see a lot of benefits in tradition. It gives a common sense of belonging and identity, it's a good reason to celebrate, and it serves as a reminder of great historical lessons. Also some traditions just *feel* good. All of those can also be said for idioms.

However, I am not one to say you should stick to something unless you see actual practical benefits. Until now I've been pushing you to strike a balance, I've presented arguments for both sides, and I've been taking the more contrarian positions. 

Yet here I am, not simply telling you to consider tradition, but instead telling you to *idolize* it. 

So what's up with that?

My biggest issue with tradition is how difficult it can be to change your environment to one with a different set of traditions. It can be due to factors ranging all the way from emotional to legal and financial. You can argue idioms are imposed on developers within the community, you can even argue that there are real, direct, practical implications on said community, which are both fair criticisms. But there is also one fundamental distinction between traditions and programming idioms: Most developers are more than able and capable to change the technology they use to build software.

This means you can change your environment to one with a very different philosophy, where the word **idiomatic**'s meaning has little to do with what it used to. Hence, a developer more often than not *prefers* the philosophy their community adheres to, they resonate with it, they've **chosen** it.

I truly adore elixir's idioms. Pattern matching is probably one of my favorite language features. I also really really love the pipe operator, I think every single language should have it. I tried to make use of those as much as possible. 

Here are my favorite examples.
```elixir
  # ExChess.Game
  defp evaluate_move(move, piece, board, special_rules) do
    with move_context = MoveContext.new(board, move, piece, special_rules),
         true <- Validators.Basic.valid?(move_context),
         normal_moves_result = Validators.NormalMoves.verify(move_context),
         {:ok, move_type} <-
           normal_moves_result || Validators.SpecialMoves.verify(move_context),
         updated_board = BoardManager.update(board, piece, move, move_type),
         false <- Validators.SquareUnderAttack.king?(updated_board, piece.color) do
      {:ok, move_type, updated_board}
    else
      _ -> :error
    end
  end

  # ExChess.Game.BoardManager
  def update(
        board,
        piece = %Piece{},
        move = %Move{},
        move_type
      ) do
    board
    |> maybe_unset_en_passant_target(piece, move, move_type)
    |> Board.set(move.to, piece)
    |> Board.unset(move.from)
    |> maybe_promote(move.to, move.promotion, piece.color)
    |> maybe_castle(piece, move, move_type)
  end
```

Even with all the complexity that surrounds both those use cases, the intent of the code is quite clear so long as it is syntax you are familiar with. Both of those also have the amazing additional benefit of making debugging so much more pleasant - you can get the output of each clause in those two functions with only 8 characters: `|> dbg()`

And for pattern matching, my favorite example is the one checking whether the castle move is allowed:
```elixir
  # ExChess.Game.Validators.SpecialMoves
  defp king_and_rook_not_moved?(%{white_queenside: true}, :castle_queenside, :white), do: true
  defp king_and_rook_not_moved?(%{white_kingside: true}, :castle_kingside, :white), do: true
  defp king_and_rook_not_moved?(%{black_queenside: true}, :castle_queenside, :black), do: true
  defp king_and_rook_not_moved?(%{black_kingside: true}, :castle_kingside, :black), do: true
  defp king_and_rook_not_moved?(_, _, _), do: false
```

And that my friends is why idioms are good, and why you should strive for them - because you **chose** them.

If you did not chose your idioms, or you do not like them, that means it's time to take that step and change environment - now's as good a time as any. Me? I love every second of them.
